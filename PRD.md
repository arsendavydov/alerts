**Версия документа:** 1.0  
**Дата создания:** 19 апреля 2026  
**Статус:** Активный

---

## 1. Обзор продукта

### 1.1 Назначение
Сервис управления алертами мониторинга - это RESTful API на базе FastAPI для централизованного управления алертами системы мониторинга. Сервис предоставляет функциональность для создания, поиска, фильтрации, подписки пользователей на алерты, управления паузами, скриншотами, связями и другими связанными сущностями.

### 1.2 Целевая аудитория
- **Операторы мониторинга** - управление алертами, настройка подписок
- **Администраторы систем** - создание и настройка алертов
- **Разработчики** - интеграция с другими системами через API
- **Менеджеры инцидентов** - управление паузами и обратной связью

### 1.3 Ключевые ценности
- ✅ Централизованное управление алертами
- ✅ Гибкая система подписок с настройкой каналов уведомлений
- ✅ Управление паузами алертов (безусловные и условные)
- ✅ Полнотекстовый поиск и фильтрация
- ✅ Интеграция с внешними системами (DT, скриншоты, ссылки)
- ✅ Асинхронная архитектура для высокой производительности

## 2. Технический стек

### 2.1 Основные технологии
- **Язык программирования:** Python 3.10
- **Фреймворк:** FastAPI 0.110.0
- **ASGI сервер:** Uvicorn 0.29.0
- **База данных:** PostgreSQL
- **Доступ к БД:** SQLAlchemy 2.0 (AsyncSession, ORM/Core), драйвер PostgreSQL - asyncpg
- **Валидация данных:** Pydantic
- **Мониторинг:** AppDynamics 25.1.0.7425

### 2.2 Архитектура
- **Паттерн:** Router -> Service -> Contracts (Protocol) -> Repository -> Models/DB
- **Dependency Injection:** FastAPI Depends + protocol-based providers
- **Асинхронность:** Полностью асинхронный код (async/await)
- **Транзакции:** AsyncSession / session scope (Unit of Work для multi-step операций)

### 2.3 Структура проекта
```
fastapi/
├── app/
│   ├── routers/       # HTTP endpoints (тонкий слой валидации)
│   ├── services/      # Бизнес-логика
│   ├── contracts/     # Protocol-контракты сервисов и репозиториев
│   ├── repositories/  # Работа с БД (SQLAlchemy ORM/Core; reflection только для динамических колонок)
│   ├── models/        # ORM-модели SQLAlchemy
│   ├── middlewares/   # Correlation-id и latency middleware
│   ├── schemas/       # Pydantic-модели для валидации
│   ├── utils/         # Утилиты (логирование, БД, исключения, context)
│   └── dependencies.py # DI контейнер
├── tests/             # Тесты (unit, integration, e2e)
├── k8s/               # Kubernetes манифесты
└── Dockerfile         # Docker образ
```

## 3. Функциональные требования

### 3.1 Модуль Alerts (Алерты)

#### 3.1.1 Поиск и фильтрация алертов
**Эндпоинт:** `GET /alerts/api/v1/alerts/search`

**Функциональность:**
- Полнотекстовый поиск по имени алерта (`alert_name`)
- Фильтрация по тегам (через запятую)
- Сортировка по полям:
  - `alert_name` (по умолчанию)
  - `indicator_name`
  - `alert_description`
  - `indicator_description`
  - `status_id`
  - `paused`
- Направление сортировки: `asc` / `desc`
- Пагинация: `limit` (1-100, по умолчанию 50), `offset` (по умолчанию 0)
- JOIN с связанными таблицами для получения полной информации

**Ответ:** Список алертов с метаданными пагинации (`total`, `limit`, `offset`)

#### 3.1.2 Автодополнение алертов
**Эндпоинт:** `GET /alerts/api/v1/alerts/autocomplete`

**Функциональность:**
- Быстрый поиск по `alert_name` для автодополнения
- Возвращает только `id` и `alert_name`
- Лимит результатов: 1-50 (по умолчанию 10)

#### 3.1.3 Получение деталей алерта
**Эндпоинт:** `GET /alerts/api/v1/alerts/detail`

**Функциональность:**
- Получение полной информации об алерте по UUID
- Включает все связанные данные (индикаторы, статусы, подписки и т.д.)

#### 3.1.4 Создание алерта
**Эндпоинт:** `POST /alerts/api/v1/alerts/detail`

**Функциональность:**
- Создание нового алерта с указанными параметрами
- Валидация уникальности имени алерта
- Генерация UUID на уровне БД (`gen_random_uuid()`), как в `cron`

**Возвращает:** `true` при успехе

#### 3.1.5 Обновление алерта
**Эндпоинт:** `PATCH /alerts/api/v1/alerts/detail`

**Функциональность:**
- Обновление существующего алерта по ID
- Частичное обновление (только переданные поля)

**Возвращает:** `true` при успехе

#### 3.1.6 Удаление алерта
**Эндпоинт:** `DELETE /alerts/api/v1/alerts/detail`

**Функциональность:**
- Удаление алерта по ID
- **Каскадное удаление:**
  - Линки (`alerts.alerts_links`)
  - Подписки (`alerts.alerts_contacts`) и их статусы (`alerts.alerts_contacts_status`)
  - История пауз (`alerts.pause_history`)
  - DT (`alerts.alerts_dt`)

**Возвращает:** `true` при успехе

#### 3.1.7 Дублирование алерта
**Эндпоинт:** `POST /alerts/api/v1/{alert_id}/duplicate`

**Функциональность:**
- Создание точной копии алерта со всем содержимым:
  - Все поля исходного алерта (кроме `id` и `alert_name`)
  - Скопированные линки
  - Скопированные подписки со всеми статусами
  - Скопированный DT (если есть)
  - Паузы **не копируются**
- Новое имя формируется как: `{старое_имя} copy - {дата_время}`

**Возвращает:** `true` при успехе

#### 3.1.8 Облако тегов
**Эндпоинт:** `GET /alerts/api/v1/alerts/tags/cloud`

**Функциональность:**
- Возвращает все уникальные теги как массив строк
- Используется для фильтрации и визуализации

#### 3.1.9 Переключение паузы алерта
**Эндпоинт:** `PATCH /alerts/api/v1/alerts/pause`

**Функциональность:**
- Безусловная пауза/снятие с паузы
- Если алерт **НЕ на паузе:** создает новую запись в `pause_history` с `start_user = login`, `end_user = NULL`, `end_time = NULL`
- Если алерт **УЖЕ на паузе:** закрывает все активные паузы, устанавливая `end_user = login` и `end_time = now()`
- Состояние паузы определяется по попаданию текущей даты в период активной паузы

**Возвращает:** `true` при успехе

### 3.2 Модуль Subscriptions (Подписки)

#### 3.2.1 Получение списка пользователей для подписок
**Эндпоинт:** `GET /alerts/api/v1/alert/{alert_id}/subscriptions/search`

**Функциональность:**
- Возвращает всех пользователей с информацией о подписке на указанный алерт
- Сортировка по полям: `user_id`, `samAccountName` (по умолчанию), `email`
- Направление сортировки: `asc` / `desc`
- Поиск по `samAccountName` или `email` (регистронезависимо, частичное совпадение)
- Фильтрация:
  - `subscribed_only`: показывать только подписанных пользователей
  - `groups`: фильтр по группам (True - группы, False - обычные пользователи)
- Пагинация: `limit` (1-100, по умолчанию 50), `offset`
- Наличие подписки определяется по наличию полей `notification_channels` и `statuses`

#### 3.2.2 Подписка пользователя на алерт
**Эндпоинт:** `POST /alerts/api/v1/alert/{alert_id}/subscriptions/users/{user_id}`

**Функциональность:**
- Подписка пользователя на алерт
- Контакты автоматически берутся из `alerts.contacts` для этого пользователя
- Создает запись в `alerts.alerts_contacts`
- Если подписка уже существует - возвращает ошибку 409

**Возвращает:** `true` при успехе

#### 3.2.3 Отписка пользователя от алерта
**Эндпоинт:** `DELETE /alerts/api/v1/alert/{alert_id}/subscriptions/users/{user_id}`

**Функциональность:**
- Отписка пользователя от алерта
- Удаляет запись из `alerts.alerts_contacts`
- Удаляет все связанные записи из `alerts.alerts_contacts_status`

**Возвращает:** `true` при успехе

#### 3.2.4 Получение подписки пользователя
**Функциональность (внутренняя):**
- Получение детальной информации о подписке пользователя на алерт
- Возвращает:
  - `subscription_id`: ID подписки
  - `notification_channels`: Динамические поля из `alerts.alerts_contacts` (булевы флаги каналов доставки: telegram, email и т.д.)
  - `statuses`: Все статусы с `send_notification=true`. Если статус есть в `alerts_contacts_status` - возвращает `repeat`, если нет - `None`

#### 3.2.5 Обновление подписки пользователя
**Эндпоинт:** `PATCH /alerts/api/v1/alert/{alert_id}/subscriptions/users/{user_id}`

**Функциональность:**
- Обновление подписки пользователя на алерт
- Обновляет:
  - `notification_channels`: Динамические поля из `alerts.alerts_contacts` (булевы флаги каналов доставки)
  - `statuses`: Статусы из `alerts.alerts_contacts_status`
    - Если статус приходит с `repeat` (включая 0) - обновить или создать
    - Если статус приходит без `repeat` (поле отсутствует) - удалить, если был

**Возвращает:** `true` при успехе

### 3.3 Модуль Pauses (Паузы)

#### 3.3.1 Получение истории пауз алерта
**Эндпоинт:** `GET /alerts/api/v1/alerts/{alert_id}/pause`

**Функциональность:**
- Возвращает паузы алерта с фильтрацией, сортировкой и пагинацией
- Фильтрация по статусу:
  - `all`: все паузы
  - `active`: активные паузы (`start_time <= now() AND (end_time IS NULL OR end_time >= now())`)
  - `future`: будущие паузы (`start_time > now() AND (end_time IS NULL OR end_time > start_time)`)
  - `past`: прошлые паузы (`end_time IS NOT NULL AND end_time < now()`)
- Сортировка по полям: `start_time` (по умолчанию DESC), `end_time`, `start_user`, `end_user`
- Пагинация: `limit` (1-100, по умолчанию 20), `offset`
- Даты возвращаются с таймзоной сервера БД (например: `2025-12-17T10:00:00+03:00`)

#### 3.3.2 Установка условной паузы
**Эндпоинт:** `POST /alerts/api/v1/alerts/{alert_id}/pause/schedule`

**Функциональность:**
- Установка паузы алерта с указанием времени начала и окончания
- Если `start_time` не указан или пустая строка - БД установит `now()`
- Если `end_time` не указан (None) или пустая строка - пауза будет бессрочной (`end_time = NULL`, `end_user = NULL`)
- `login` используется для `start_user` (всегда) и для `end_user` (если указан `end_time` и не пустая строка)
- Даты должны передаваться с таймзоной (например: `2025-12-17T10:00:00+03:00`)

**Возвращает:** `true` при успехе

#### 3.3.3 Остановка всех активных пауз
**Эндпоинт:** `PATCH /alerts/api/v1/alerts/{alert_id}/pause/stop`

**Функциональность:**
- Останавливает все активные паузы алерта
- Устанавливает `end_time = now()` и `end_user`
- Если `end_time` уже был указан - перезаписывается на `now()`
- Если `end_user` уже был указан - перезаписывается на переданный

**Возвращает:** `true` при успехе

#### 3.3.4 Изменение условной паузы
**Эндпоинт:** `PATCH /alerts/api/v1/alerts/{alert_id}/pause/{pause_id}`

**Функциональность:**
- Изменение условной паузы алерта
- Можно изменить `start_time` и/или `end_time`
- Если `start_time` - пустая строка, установится `now()`
- Если `end_time` - пустая строка, пауза станет бессрочной (`end_time = NULL`, `end_user = NULL`)
- Если указан `start_time` или `end_time` (не пустая строка), обязательно указать `login`
- Переданные поля перезаписываются в БД

**Возвращает:** `true` при успехе

#### 3.3.5 Остановка конкретной паузы
**Эндпоинт:** `PATCH /alerts/api/v1/alerts/{alert_id}/pause/{pause_id}/stop`

**Функциональность:**
- Останавливает конкретную паузу алерта
- Если пауза активна - устанавливает `end_time = now()` и `end_user`
- Если пауза в будущем - устанавливает `end_time = start_time` и `end_user` (пауза так и не начнется)
- Если пауза в прошлом - возвращает ошибку 400

**Возвращает:** `true` при успехе

#### 3.3.6 Удаление паузы
**Эндпоинт:** `DELETE /alerts/api/v1/alerts/{alert_id}/pause/{pause_id}`

**Функциональность:**
- Удаляет конкретную паузу из истории алерта по её ID
- Полностью удаляет запись из `alerts.pause_history`

**Возвращает:** `true` при успехе

- Лимит результатов: 1-100 (по умолчанию 50)

## 4. Нефункциональные требования

### 4.1 Производительность
- **Время отклика API:** < 500ms для большинства запросов
- **Пропускная способность:** Поддержка до 1000 запросов в секунду
- **Асинхронность:** Все операции с БД выполняются асинхронно через SQLAlchemy AsyncSession
- **Пул соединений:** Управление через async engine SQLAlchemy

### 4.2 Масштабируемость
- **Горизонтальное масштабирование:** Поддержка нескольких инстансов через Kubernetes
- **Воркеры:** Настраиваемое количество воркеров Uvicorn через переменную окружения `WORKERS_COUNT`
- **База данных:** Поддержка репликации и шардинга PostgreSQL

### 4.3 Надежность
- **Обработка ошибок:** Централизованные обработчики исключений
- **Валидация данных:** Валидация всех входных данных через Pydantic
- **Транзакции:** Использование транзакций для критических операций
- **Логирование:** Структурированное логирование с `correlation_id`, latency и настраиваемым уровнем (`LEVEL_LOG`)

### 4.4 Безопасность
- **Валидация входных данных:** Все входные данные валидируются через Pydantic схемы
- **SQL Injection защита:** Использование SQLAlchemy выражений и параметризованных запросов
- **UUID валидация:** Все ID валидируются как UUID
- **Обработка ошибок:** В non-debug режиме скрываются внутренние детали 5xx; в `LEVEL_LOG=DEBUG` trace может быть добавлен в ответ для диагностики
- **Trust boundary:** сервис считается internal-only; аутентификация/авторизация и сетевые политики обеспечиваются внешним периметром (ingress/API-gateway/service-mesh).

### 4.5 Мониторинг
- **Health Check:** `GET /alerts/health` для проверки работоспособности
- **AppDynamics:** Интеграция с AppDynamics для мониторинга производительности
- **Логирование:** Структурированные логи с `X-Correlation-ID` и `latency_ms` для трассировки запросов
- **HTTP observability:** `X-Correlation-ID` возвращается в каждом HTTP-ответе

## 5. Формат ответов API

### 5.1 Успешные ответы
Все успешные ответы возвращаются в формате JSON:
- **Создание/Обновление/Удаление:** `true` (boolean) или объект с данными
- **Списки:** Объект с массивом данных и метаданными пагинации:
  ```json
  {
    "items": [...],
    "total": 100,
    "limit": 50,
    "offset": 0
  }
  ```
- **Детали:** Объект с полной информацией о сущности

### 5.2 Ошибки
Базовый формат ошибок - JSON-объект:
```json
{
  "status": "error",
  "message": {
    "type": "HTTPException",
    "error": "Описание ошибки",
    "trace": null
  }
}
```

Примечание: для части стандартных FastAPI/валидационных сценариев может возвращаться совместимый формат с полем `detail`.

**Коды статусов:**
- `200` - Успешный запрос
- `400` - Ошибка валидации данных
- `404` - Ресурс не найден
- `409` - Конфликт (например, дублирование подписки)
- `500` - Внутренняя ошибка сервера
